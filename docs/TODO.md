  FOUND 2026-09-01 in live use on the Enix tracker; reproduced deliberately afterwards.

      $ trk add --tags=a,b "Fixture title that should not be blamed"
      trk: unknown flag 'Fixture title that should not be blamed'

  The unknown flag is `--tags=a,b` (the correct spelling is `--tag <t>`, repeatable). The title is a
  perfectly well-formed positional and is the ONE argument in the line that is right. The parser
  evidently swallowed `--tags=a,b` into the title slot, then met the real title as an unexpected second
  positional and reported THAT as a flag.

  COST, and it is the reason this is worth fixing rather than shrugging at: the message sends you to
  inspect your title. Mine was long, contained backticks and an em dash, and had been written through a
  shell heredoc -- so I spent a cycle hunting a quoting bug in an argument that was never the problem,
  before noticing the flag name. A message that named `--tags=a,b` would have cost seconds.

  FIX SHAPES, either would do:
    * report the ARGUMENT THAT FAILED TO PARSE, not the one that arrived unexpectedly afterwards; or
    * when an unknown token begins with `--`, say so explicitly and, if a near-match exists among the
      known flags, name it -- `--tags` -> `--tag` is a one-character edit distance and the plural is the
      natural guess for a repeatable flag.
  The second is strictly better here: the whole class of error is someone reaching for the plural of a
  repeatable option.

  RELATED SHAPE, same session, not the same bug: `--tags=` is also a plausible spelling because several
  OTHER trk flags do take `=`-joined values. Worth a look at whether the repeatable flags are
  discoverable as repeatable from `--help` alone.

- [ ] `01M1FMN25` next/list --json omit the BODY, so the mechanical full-frontier triage a fan-out mandates cannot be scripted -- and the markers that decide a task's bucket live only in the body, at its tail #cli #json

  <details><summary>FOUND 2026-09-01 while triaging a 280-task ready frontier for an away…</summary>

  FOUND 2026-09-01 while triaging a 280-task ready frontier for an away fan-out.

      trk next --json | python3 -c "...print(sorted(d[0].keys()))"
      ['id', 'priority', 'seq', 'short', 'state', 'tags', 'title']

  No `body`. Same for `trk list --json`.

  WHY IT BITES rather than being a nice-to-have. Enix's fan-out skill REQUIRES a mechanical triage of
  EVERY ready task before an orchestrator may claim the autonomous work is exhausted -- explicitly "the
  WHOLE list, scripted over tags + title keywords, not the top N, not a sample". The discriminators that
  decide which bucket a task lands in are `HOLD`, `DEFER`, `RULED`, `scott-decision`, "NOT resolved",
  "your call" -- and the skill is emphatic that these are APPENDED, so they sit at the END of a long
  body while the opening paragraphs still read like ordinary buildable work. Every one of those signals
  is invisible to `--json`.

  The practical result on 280 tasks: tags and titles were scriptable, and everything else needed a
  `trk show` per candidate. That is precisely the step where I repeatedly found tasks whose work was
  already done, already ruled, or blocked on someone else -- the expensive discovery the triage exists
  to make cheap.

  TRK ALREADY HAS THE BODY IN HAND at that moment: `trk next --help` says its search terms match "over
  title+body+tags", so the filter reads the body and the emitter drops it.

  FIX SHAPES:
    * simplest -- include `body` in `--json` unconditionally. The consumer is a machine; size is not the
      concern it would be for the human view.
    * if size IS a concern (a 3 MB render is not hypothetical here), a `--json-full` / `--with-body`
      flag, or a `--body-tail <n>` emitting the last n lines, which is where the markers actually are.
    * cheapest useful subset if neither appeals: a boolean per task for whether the body matches any of
      the decision markers, so a triage script can at least SEE which rows need a `show`.

  WORTH DECIDING rather than defaulting: the third option encodes Enix's marker vocabulary into trk,
  which is arguably the wrong layer. The first keeps trk generic and pushes the grep to the caller. I
  would take the first.

  `git log -S` finds all three cited in the very commits that landed their rows (b0fc533f, d4a5a455,

  the record is simply gone.

  WHY THAT IS WORSE THAN AN ARCHIVED ID. Seven sibling rows in the same audit were resolved by READING
  the archived owner's body and seeing whether a verification had actually happened -- three were
  cleared on the strength of a recorded PASS, four got fresh owners because their bodies showed a
  feature landing with no boot. For a GC'd id there is no body to read, so "verified, write-back
  forgotten" is indistinguishable from "never booted" and the only honest state is the unverified one
  the rows already carry. A week of gate-governance provenance was destroyed silently.

  THE DESIGN GAP. trk's compaction rules were written about task-to-task references -- `needs` edges,
  arcs, citations inside other task bodies, all of which trk can see. They say nothing about ids cited
  from files OUTSIDE the tracker, which trk cannot see and which are, in this project, load-bearing:
  a registry column, a source comment, a design doc, a commit message.

  SHAPES, none obviously right, which is why this is filed rather than fixed:
    * a pre-compact WARNING listing ids about to be GC'd, so a caller can grep its own tree first. Cheap,
      keeps trk ignorant of its consumers, puts the check where the knowledge is. Probably the answer.
    * an opt-in "cited externally" pin (a tag, or a config-listed glob trk greps before compacting).
      More capable, more coupling.
    * tombstones -- keep id + title + final state forever, GC only the body. Answers "did this exist and
      what was it" without unbounded growth, which is exactly the question a dangling citation asks.
    * rule it a caller responsibility and say so in design.md, so the next person hits documentation
      instead of a mystery.

  RELATED, not the same: `dangling-tracker-id-lint.sh` on the Enix side checks id EXISTENCE and its own
  selftest asserts that a citation of a COMPACTED/ARCHIVED id PASSES -- deliberately, so archival does
  not redden a tree. That is a defensible rule for archived ids and it is why nothing caught these.

- [s] `01M2GJV9S` trk mcp-serve: expose the verb table as MCP tools over stdio, so masked exits, shell-executed backticks, swapped positionals and direction-less body edits are unrepresentable -- every tool takes a required tree selector because subagents share the session's one server #mcp #agent-surface

  <details><summary>`trk mcp-serve`: trk speaks MCP (JSON-RPC 2.0, newline-delimited, over…</summary>

  `trk mcp-serve`: trk speaks MCP (JSON-RPC 2.0, newline-delimited, over stdio) so an agent calls typed tools
  instead of shelling out. Filed from the Enix side, where it is task 01M29TMPQ in arc 01M29TM00 (the house tools
  getting MCP front ends). The Enix task keeps the adoption half: registering the server, moving CLAUDE.md and
  the skills, and verifying against the Enix store.

  WHY -- every item is a recorded incident on the Enix tracker, not a hypothesis. Each is a SHELL failure that
  a typed tool call makes unrepresentable rather than discouraged:
    * MASKED EXITS. `trk state <id> done | tail -1` reports tail's exit; an orchestrator did it on nearly every
      close in one session (2026-09-11). A tool result has no pipe.
    * BACKTICKS EXECUTING AS SHELL inside `--body`/`--append-body` text. Bodies are exactly where code
      identifiers and shell snippets belong, so this is the highest-traffic hazard.
    * SWAPPED POSITIONALS -- the reason `dep` refuses the two-positional form. Named parameters make the swap
      unrepresentable.
    * A BODY EDIT WITH NO DIRECTION -- as a required enum (append | replace) it cannot be omitted, and the
      destructive one is named at every call site.
    * VERB SCOPE. `archive`/`compact`/`render` are orchestrator-only, and a lane ran `render` anyway because
      the rule lived in prose it never read.

  SHAPE
    * `trk mcp-serve`: initialize (declare the tools capability), tools/list, tools/call; ignore id-less
      notifications. Stdout carries protocol only; diagnostics go to stderr. std-only, like the rest of trk.
    * The tool schema is DERIVED FROM THE SAME VERB TABLE `main` dispatches on, so CLI and MCP cannot drift.
      Every tool calls the same code the CLI verb calls -- never a reimplementation. Bodies in particular
      must go through trk's own snapshot+log fold: a caller reading log.jsonl directly sees a body last
      written before the newest compact as EMPTY and truncates it.
    * Read verbs (show, list, next, tree, log) return structured JSON content, not formatted text -- which
      also removes the reason anyone pipes them.
    * States in the schema are the post-rename ones (01M2GGFGR): `submitted` is the completion report;
      `claimed` requires a holder; release is its own tool.
    * The CLI stays the primary surface -- docs cite it, humans use it, it works over ssh. MCP is an
      additional front end. A change that deprecates CLI verbs has overstepped.

  TREE SELECTION -- the constraint that shapes every tool (ruled by Scott, 2026-09-14: expose it as an option)
    Measured: Claude Code spawns a stdio MCP server ONCE PER SESSION from .mcp.json, cwd = the session's repo
    root, and SUBAGENTS share that one process (they run inside the parent session and multiplex over its
    pipe). So a lane working in a git worktree reaches a server whose cwd is the MAIN checkout, and trk's
    walk-up discovery would silently retarget every lane write from its worktree's .tracker/ to main's.
    Therefore every tool takes a REQUIRED `tree` parameter: "main", or a worktree path. No default -- same
    named-at-the-call-site argument as the body direction. A path that is not a linked worktree of the
    server's repo is REFUSED, never silently resolved elsewhere (trk already recognizes a linked worktree by
    its `.git` FILE; how to validate membership without shelling out to git is the builder's call -- record
    it in design.md).
    Which tree a write belongs in turns on one question: is the fact true only if the lane's commit lands?
      * yes -> the worktree: `submitted`, and edits describing what the lane's change did.
      * no  -> main: the `claimed` lease and its release, and defects/follow-ons a lane discovers (filed in
        a worktree they die with an abandoned lane).
    The server enforces only the tree's validity, not this policy; the policy is the caller's, stated per call.

  VERB SCOPE -- note for the design, not a settled shape
    Because subagents share the session's one server, the server cannot tell an orchestrator's call from a
    lane's, so hiding `archive`/`compact`/`render` cannot be done server-side by caller. What can scope it:
    per-agent-type tool allowlists on the Claude Code side (an agent definition names the MCP tools it gets),
    which needs those verbs to be separate tools rather than one generic `trk` tool with a verb argument.
    So: one MCP tool per verb.

  WHERE THIS SITS (ruled by Scott, 2026-09-14)
    * trk SERVES ITS OWN MCP, because it has its own repo -- not through a wrapper that shells out to it.
    * The other house tools do not get per-tool servers. A CROSS-PROJECT core MCP server, in its own repo and
      registered user-wide, carries enixedit (extracted from the Enix tree and renamed) plus generic Bash
      replacements (process kill, wait-for-condition, run a Windows exe, git). An in-repo Enix server carries
      enixnet-zig plus Enix's gate/build verbs.
    * So trk and the core server will both be Zig stdio JSON-RPC servers outside Enix. Build the protocol loop
      for trk's needs; whether the two later share a small helper is worth a look once both exist, and trk
      does not wait on it.

  VERIFICATION: host tests here (protocol round-trip: initialize, tools/list, tools/call for a read and a
  write verb; a `tree` pointing outside the repo's worktrees is refused; a body append through MCP after a
  compact keeps the snapshot-only body). The Enix side then registers it and verifies against its store.

  </details>
